IMAGE-TO-G-CODE REPLIT IMPLEMENTATION
=====================================

Purpose
-------

This document describes the current Image-to-G-Code implementation in the
DMHC-EM Replit project. It is intended as an implementation specification for
reproducing the same behavior in another copy of the project.

The current implementation is a JSON/Data-URL API flow. It is not a multipart
upload flow. The generated G-code is placed in the existing Workspace editor,
but it is not compiled or sent to a CNC machine automatically.

3.4 decodeImageData
--------------------

Function:
decodeImageData

Inputs:
imageData: string

Outputs:

{
  mimeType: string;
  bytes: Buffer;
}

Behavior:

1. Requires a supported image Data URL.
2. Removes whitespace from the base64 payload.
3. Decodes the payload with Buffer.from(..., "base64").
4. Rejects empty bytes.
5. Rejects decoded files larger than 10 MiB with status 413.

It does not accept a filesystem path, raw multipart file, or arbitrary URL.

3.6 readImageMetadata
----------------------

Function:
readImageMetadata

Inputs:
inputPath: string

<inputPath> -format "%m %w %h" info:

Outputs:

{
  format: string;
  width: number;

Behavior:

* Only PNG, JPEG, and WEBP metadata is accepted.

3.7 getRasterSize
------------------

Function:
getRasterSize

Inputs:
width: number
height: number

Output:

{
  width: number;
  height: number;
}

Behavior:

The image is downsampled only when either source dimension is greater than
480. The scale is:

min(1, 480 / width, 480 / height)

Each output dimension is:

max(2, round(sourceDimension * scale))

The original source dimensions remain available in the response as
sourceWidth and sourceHeight.

3.8 buildBinaryMask
--------------------

Function:
buildBinaryMask

Inputs:

pixels: Buffer
width: number
height: number
threshold: number

Output:

Uint8Array with width * height entries.

Exact pixel rule:

pixels[index] <= threshold ? 1 : 0

Therefore:

* Dark pixels are drawing pixels.
* White pixels are normally background.
* Equality with the threshold is included as drawing.
* Polarity is fixed; there is no inversion option.

3.9 removeSmallComponents
--------------------------

Function:
removeSmallComponents

Inputs:

mask: Uint8Array
width: number
height: number

Output:

Cleaned Uint8Array.

Algorithm:

* Uses breadth-first traversal of foreground connected components.
* Connectivity comes from the eight-neighbor getNeighbors function.
* The minimum component size is:

  max(2, min(12, floor(width * height / 50_000)))

* Components smaller than this value are dropped.
* Components at or above this value are copied to the output mask.

At the normal 480 x 480 working size the minimum is 4 pixels. For the small
80 x 60 test images it is 2 pixels.

3.10 skeletonize
-----------------

Function:
skeletonize

Inputs:

mask: Uint8Array
width: number
height: number

Output:

Uint8Array containing a thinned foreground skeleton.

Algorithm:

* Starts with a copy of the cleaned binary mask.
* Repeats until no pixels change or 200 iterations have been reached.
* Each iteration has two Zhang-Suen-style deletion passes.
* For each foreground pixel, the eight neighbors are read in clockwise order.
* A pixel is considered only when its neighbor count is 2 through 6.
* The number of 0-to-1 cyclic transitions must equal 1.
* Each pass applies its own north/east/south/west deletion conditions.
* Deletions are collected first and applied after the scan for that pass.

3.11 getNeighbors
------------------

Function:
getNeighbors

Inputs:

mask: Uint8Array
index: number
width: number
height: number

Output:

An array of foreground pixel indexes.

The function considers all eight surrounding directions. It suppresses a
diagonal edge when the two diagonal pixels are already connected through an
orthogonal foreground bridge. This prevents a thinned rectangle corner from
becoming a small triangular graph with duplicate short paths.

3.12 traceSkeletonPaths
------------------------

Function:
traceSkeletonPaths

Inputs:

skeleton: Uint8Array
width: number
height: number

Output:

VectorPath[]

Algorithm:

1. Compute the graph degree of each foreground pixel.
2. Use an edge key based on the two endpoint indexes, independent of direction.
3. Mark traversed edges in visitedEdges.
4. First trace edges from pixels whose degree is not 2.
5. Then trace any remaining unvisited edges, including closed loops.
6. Continue through degree-2 pixels until a branch, an already visited edge, or
   the starting point is reached.
7. Mark a path closed when the trace returns to its starting pixel.

This is a centerline graph tracer, not a filled-region contour hierarchy
algorithm.

3.13 perpendicularDistance and simplifyPolyline
------------------------------------------------

Functions:

perpendicularDistance
simplifyPolyline

Inputs:

RasterPoint arrays and a tolerance.

Output:

A reduced RasterPoint array.

The current tolerance is:

1.25 raster pixels

The implementation is recursive Ramer-Douglas-Peucker simplification. Consecutive
duplicate points are removed before and after simplification.

3.14 dedupePoints
------------------

Function:
dedupePoints

Removes only consecutive points with identical x and y values. It is not a
global geometric duplicate-path detector.

3.15 snapAxisAlignedRectangle
--------------------------------

Function:
snapAxisAlignedRectangle

Inputs:
RasterPoint[] after simplification.

Output:
RasterPoint[].

Behavior:

The function returns the original points unless all of the following are true:

* The path contains 4 through 6 points.
* Points can be mapped to four distinct bounding-box corners.
* The resulting consecutive edges are horizontal or vertical.
* Every original point is within 2.5 raster pixels of its mapped corner.

When all conditions pass, the points are replaced with the mapped bounding-box
corners. This is a narrow rectangle heuristic. It does not snap arbitrary
curves, circles, logos, or technical drawings.

3.16 cleanVectorPath
---------------------

Function:
cleanVectorPath

Inputs:
VectorPath

Output:
VectorPath or null.

Behavior:

* Remove consecutive duplicate points.
* Apply RDP simplification with tolerance 1.25.
* Discard paths with fewer than two points.
* For closed paths, remove a repeated last point when it equals the first.
* Require at least three points for a closed path.
* Apply the guarded rectangle snap only to closed paths.
* Preserve the closed flag.

3.17 extractVectorPaths
-----------------------

Function:
extractVectorPaths

Inputs:

pixels: Buffer
width: number
height: number
threshold: number

Output:

VectorPath[]

Pipeline:

buildBinaryMask
-> removeSmallComponents
-> skeletonize
-> traceSkeletonPaths
-> cleanVectorPath
-> discard null paths
-> limit to the first 2,000 paths

If no path remains, it throws:

No drawable content was detected in the image.

There is no separate global geometric duplicate-path comparison. Edge visitation
and consecutive-point cleanup provide the current duplicate prevention.

3.18 formatNumber
------------------

Function:
formatNumber

Behavior:

* Rejects non-finite numbers.
* Uses toFixed(3).
* Removes trailing zeroes and a trailing decimal point.

Examples:

5.000 -> 5
0.000 -> 0
12.340 -> 12.34

3.19 orderPaths
----------------

Function:
orderPaths

Inputs:
VectorPath[]

Output:
Ordered VectorPath[].

Algorithm:

* Starts from raster point { x: 0, y: 0 }.
* For each remaining path, compares the squared distance to its first and last
  points.
* Selects the closest path endpoint.
* Reverses the path when its last endpoint is closer than its first endpoint.
* Repeats until no paths remain.

This is a nearest-endpoint greedy ordering algorithm. It is not a global
traveling-salesperson optimizer.

3.20 buildGcode
----------------

Function:
buildGcode

Inputs:

paths: VectorPath[]
rasterWidth: number
rasterHeight: number
options: ImageToGcodeOptions
sourceWidth: number
sourceHeight: number

Output:
ImageToGcodeResult

Fitted drawing dimensions:

fitScale = min(maxX / sourceWidth, maxY / sourceHeight)
width = sourceWidth * fitScale
height = sourceHeight * fitScale
offsetX = (maxX - width) / 2
offsetY = (maxY - height) / 2

The image aspect ratio is therefore preserved. The drawing is centered inside
the requested maxX by maxY workspace.

Raster-to-machine conversion:

x = clamp(
  offsetX + (point.x / max(1, rasterWidth - 1)) * width,
  0,
  maxX
)

y = clamp(
  offsetY +
    ((rasterHeight - 1 - point.y) / max(1, rasterHeight - 1)) * height,
  0,
  maxY
)

The Y expression reverses the raster row direction so machine Y increases
upward. The clamp is applied to every converted point.

For each ordered path:

1. Rapid to the first XY point with pen up.
2. Move to penDownZ with feed 1000.
3. Emit every remaining path point with feed 2000.
4. If the path is closed, emit the first point again to close it.
5. Return to penUpZ.

The response width and height are the fitted drawing dimensions, while
sourceWidth and sourceHeight are the decoded original image dimensions.

3.21 validateGeneratedGcode
----------------------------

Function:
validateGeneratedGcode

Inputs:

gcode: string
maxX: number
maxY: number
penDownZ: number
penUpZ: number

Output:

{
  xMin: number;
  xMax: number;
  yMin: number;
  yMax: number;
}

Algorithm:

* Split the G-code into lines.
* Remove semicolon comments before reading coordinates.
* Parse X, Y, and Z values with a case-insensitive coordinate regular
  expression.
* Reject non-finite coordinate values.
* Calculate min and max X and Y.
* Use a tolerance of 0.0005.
* Reject X below -tolerance or above maxX + tolerance.
* Reject Y below -tolerance or above maxY + tolerance.
* Reject every Z value that is not within tolerance of either penDownZ or
  penUpZ.

This validation runs after G-code generation and before the result is returned.

3.22 generateImageToGcode
--------------------------

Function:
generateImageToGcode

Inputs:
ImageToGcodeOptions

Output:
Promise<ImageToGcodeResult>

Exact flow:

1. Validate numeric options.
2. Decode the supported Data URL.
3. Create a temporary directory named with the
   dmhc-image-to-gcode- prefix.
4. Write the decoded bytes to source-image.
5. Read metadata with ImageMagick.
6. Verify declared MIME type against decoded ImageMagick format.
7. Calculate the working raster dimensions, capped at 480 per side.
8. Invoke ImageMagick to:
   - remove the alpha channel over a white background,
   - convert to Gray,
   - resize to the working raster dimensions,
   - write 8-bit raw grayscale bytes.
9. Read grayscale.raw and verify the expected byte count.
10. Extract vector paths using extractVectorPaths.
11. Generate and validate G-code using buildGcode.
12. Always remove the temporary directory in finally, including errors.

5. THRESHOLD IMPLEMENTATION
===========================

Minimum:
0

Maximum:
255

Default:
128

Frontend validation:

In Home, the string state imgThreshold is converted with Number(...). It is
valid only when:

* the input is not empty,
* Number.isInteger(imgThresholdNum) is true,
* the value is >= 0,
* the value is <= 255.

Invalid input marks the field as destructive and disables image generation.

Backend validation:

The generated Zod schema checks the number is between 0 and 255. The
implementation validates again with Number.isInteger and the same inclusive
range.

Pixel polarity:

The exact drawing condition is:

grayscalePixel <= threshold

Dark pixels are treated as drawing. White pixels are treated as background
unless threshold is high enough to include them.

Inversion:

NOT IMPLEMENTED. There is no inversion checkbox or inversion API field.

Threshold = 0:

Only pixels with grayscale value exactly 0 are included. In practice this
selects pure black pixels and excludes gray pixels and white background.

Threshold = 128:

Pixels with grayscale values from 0 through 128 inclusive are included.
This is the default.

Threshold = 255:

All 8-bit grayscale values from 0 through 255 inclusive satisfy the mask
condition. This can include the white background and may produce substantially
different geometry depending on the image.

Invalid values:

* -1: rejected.
* 256: rejected.
* 12.5: rejected because it is not an integer.
* NaN, Infinity, and -Infinity: rejected as non-finite.


6. MACHINE DIMENSION LIMITS AND SCALING
=======================================

Hard limits:

X maximum = 300 mm
Y maximum = 615 mm

Backend source:

IMAGE_TO_GCODE_LIMITS in
artifacts/api-server/src/lib/image-to-gcode.ts

Backend validation:

maxX > 0 and maxX <= 300
maxY > 0 and maxY <= 615

Generated Zod schema:

maxX minimum = 0.0001
maxX maximum = 300
maxX default = 300

maxY minimum = 0.0001
maxY maximum = 615
maxY default = 615

Frontend defaults:

imgMaxX = "300"
imgMaxY = "615"

Frontend validation:

maxX is finite, greater than 0, and no greater than 300.
maxY is finite, greater than 0, and no greater than 615.

Scaling:

The source aspect ratio is preserved. The image is uniformly scaled to fit
inside maxX by maxY:

fitScale = min(maxX / sourceWidth, maxY / sourceHeight)

The unused dimension is centered with offsetX or offsetY.

Coordinate safety:

* Every converted point is clamped to 0 through maxX and 0 through maxY.
* The complete generated G-code is parsed again.
* Final validation rejects any coordinate outside the requested workspace,
  with a tolerance of 0.0005.

The implementation therefore rejects invalid requested dimensions and refuses
to return generated G-code whose X/Y coordinates exceed the configured
workspace limits.


7. Z AXIS AND PEN CONTROL
=========================

Image conversion defaults:

penDownZ = 0
penUpZ = 5

Frontend state:

imgPenDownZ = "0"
imgPenUpZ = "5"

The values are editable numeric inputs. They must be non-empty finite numbers
in the frontend. The backend also requires finite numbers.

Travel:

Every path starts with:

G0 X... Y...
G1 Z<penDownZ> F1000

The path is drawn with G1 XY commands at F2000. Every disconnected path ends
with:

G0 Z<penUpZ>

The initial header also raises the pen. The final footer raises it again.

Representative output:

G0 Z5
G0 X18.987 Y400.932
G1 Z0 F1000
G1 X281.013 Y400.932 F2000
G1 X281.013 Y214.068 F2000
G1 X18.987 Y214.068 F2000
G1 X18.987 Y400.932 F2000
G0 Z5

No machine is contacted during image conversion.


8. G-CODE GENERATION
====================

Header:

; DMHC image-to-gcode vector paths
G21
G90
G0 Z<penUpZ>

G21 selects millimetres.
G90 selects absolute coordinates.

Feeds:

Pen down:
G1 Z<penDownZ> F1000

Drawing moves:
G1 X<value> Y<value> F2000

Rapid moves:

G0 Z<penUpZ>
G0 X<value> Y<value>

Closed path behavior:

If a VectorPath has closed = true, the first machine point is emitted again
after the other points:

G1 X<startX> Y<startY> F2000

This closes a rectangle or other closed loop.

Footer:

; End vector drawing
G0 Z<penUpZ>

Decimal formatting:

* Values are rounded/formatted with toFixed(3).
* Trailing zeroes and a trailing decimal point are removed.
* Maximum visible precision is three decimal places.
* Non-finite values are rejected.

Command ordering for every path:

G0 Xstart Ystart
G1 ZpenDown F1000
G1 Xpoint Ypoint F2000
...
G1 Xstart Ystart F2000       (closed paths only)
G0 ZpenUp

commandCount is the number of generated lines in the lines array, including
comments and the final footer commands. It is not limited to only motion
commands.

1. Stops when there is no image, invalid settings, or an active conversion.
2. Captures the current File and numeric settings locally.
3. Sets status to reading-image.
4. Reads the file with FileReader.readAsDataURL.
5. Sets status to processing.
6. Calls generateGcode.mutate with:

   {
     imageData: base64Data,
     maxX: currentMaxX,
     maxY: currentMaxY,
     penDownZ: currentPenDownZ,
     penUpZ: currentPenUpZ,
     threshold: currentThreshold
   }

7. On success, sets status to loading-workspace.
8. After a 300 ms timeout:
   * sets gcodeContent to res.gcode,
   * changes the filename extension to .gcode,
   * sets status to success,
   * displays "Generated <pathCount> paths.",
   * scrolls to the existing G-code input area.
9. On API error, sets status to error and displays the error.
10. On FileReader error, sets status to error and displays the read error.

The 300 ms delay is UI sequencing only; it does not run the compiler.

17. BEFORE / AFTER CODE BEHAVIOR
================================

Before:

The previous implementation scanned image rows and generated repeated
horizontal drawing segments for dark pixels. That behavior was raster-like and
could produce many horizontal lines for a single shape.

After:

The current implementation:

* Converts the image to grayscale.
* Creates a thresholded binary mask.
* Removes small connected components.
* Thins the mask into a skeleton.
* Traces the skeleton graph.
* Simplifies paths with RDP.
* Uses closed vector-like paths for rectangle outlines and other loops.
* Uses a centerline for simple strokes.
* Emits compact G1 paths with explicit pen-up travel between disconnected
  paths.

The old row-by-row scanline behavior is not used by the current image
converter. Search result:

extractPixelPaths: NOT FOUND in the current implementation.

The word "scanlines" appears only in test descriptions that assert the new
behavior is not scanline output. There is no active old scanline converter
function in the current implementation.


18. IMPORTANT ALGORITHM DETAILS
================================

Threshold polarity:

grayscale <= threshold is drawing.

Image inversion:

NOT IMPLEMENTED.

Coordinate origin:

The raster origin is the top-left image pixel. Machine coordinates are
bottom-left-oriented because raster Y is inverted during conversion.

Y direction:

Machine Y increases as image rows move upward.

Image-to-machine conversion:

Uniform fitScale based on original source dimensions, centered in the
requested workspace, followed by raster point normalization and clamping.

Rounding:

Machine coordinates are formatted to a maximum of three decimal places.

Path simplification:

Ramer-Douglas-Peucker with tolerance 1.25 raster pixels.

Component filtering:

Minimum connected-component size:

max(2, min(12, floor(width * height / 50_000)))

Path limit:

Only the first 2,000 cleaned paths are retained. The implementation does not
return an error when more than 2,000 paths are found; it truncates the list.

Contour hierarchy:

NOT IMPLEMENTED as a separate data structure. Nested shapes are represented as
separate traced paths when the skeleton graph yields separate paths.

Closed-path detection:

A trace is marked closed when it returns to its starting graph pixel.

Open-path detection:

A trace that ends at a branch, unvisited boundary, or non-returning endpoint
remains open. Open paths are not explicitly closed in G-code.

Duplicate cleanup:

Consecutive identical points are removed. Graph edges are marked visited.
Global geometric duplicate-path comparison is NOT IMPLEMENTED.

Rectangles:

Near-four-corner closed loops are snapped to bounding-box corners only when
they are within 2.5 raster pixels and produce four axis-aligned corners.

Circles:

No dedicated circle heuristic is implemented.

Thin lines:

Skeletonization and graph tracing produce centerline-like paths. A horizontal
stroke test produces one path and one cut move, not one path per image row.

Logos and technical drawings:

No dedicated logo or CAD/technical-drawing mode is implemented. They use the
same threshold, component, skeleton, graph, and RDP pipeline.

Aspect ratio:

Preserved by the uniform fitScale calculation.

Machine bounds:

Protected first by maxX/maxY option validation, then by point clamping, then by
final G-code parsing and validation.
