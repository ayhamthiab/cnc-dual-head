RASPBERRY PI ARM64 COMPATIBILITY AND DEPENDENCY AUDIT
=====================================================

Scope and method
----------------
Analysis only. No source, configuration, dependency, or project files were
modified. This report was produced from a recursive workspace inventory; all
application source, build/dependency manifests, startup scripts, relevant
configuration, lockfile platform entries, and the existing virtual environment
package inventory were inspected. Attached prompt/history files and images were
identified but are not runtime code.

Target: Raspberry Pi OS/Debian, Linux aarch64, kernel 6.18.34+rpt-rpi-v8.
Source host: Windows 10.

EXECUTIVE VERDICT
----------------
The project can realistically run on a Raspberry Pi ARM64, but it is NOT
ready to transfer and start unchanged. The Java machine agent source is mostly
cross-platform and has the best chance of working after a native Pi build.
The frontend/API have Linux ARM64 packages in their lockfile and should build
on a Pi after a clean pnpm install. The current Windows launcher/installer
cannot run there. Physical CNC control remains a hardware validation task,
not a guarantee: JSerialComm supports Linux ARM architectures, but UGS Core
and the specific USB serial adapters/controllers must be tested on the target.

The most material blockers before production use are:
1. No Linux/Raspberry Pi launcher or systemd units exist.
2. Linux serial-device permissions and stable USB naming are not configured.
3. The source still contains Windows-oriented operational wording and launch
   discovery; local_desktop_app.py actively runs PowerShell to clear ports.
4. Image-to-G-code API requests require ImageMagick's `magick` command.
   The separate Python image_to_gcode module additionally requires OpenCV,
   NumPy, Potrace and vpype, none of which are declared in requirements.txt.
5. The Pi must build/install its own node_modules, Python venv, UGS Core, and
   Machine Agent JAR. Windows binaries and venv/node_modules must not be copied.

WINDOWS-SPECIFIC FINDINGS
-------------------------
1. start_local_project.bat (entire file)
   Uses cmd syntax, `%~dp0`, `set`, `pause`, backslashes and C:\gp\.venv;
   probes .venv\Scripts\python.exe. Cannot run on Linux. Code/startup script
   replacement required (proposed start_raspberry_pi.sh).

2. local_desktop_app.py: kill_port, _append_windows_tool_dirs,
   find_java_and_maven, start_services
   `powershell -NoProfile -Command Get-NetTCPConnection ... Stop-Process` is
   Windows-only. C:\Program Files Java/Maven paths, java.exe/mvn.cmd/mvn.exe
   discovery and Windows Scripts directories are Windows-specific. On Linux,
   the port cleanup silently does nothing; environment/path augmentation is
   already skipped when os.name != nt. Requires code change for equivalent
   Linux stale-process handling, or avoid this launcher and start services
   separately/systemd.

3. artifacts/api-server/src/routes/jobs.ts:getPythonCommand/getWorkspaceRoot
   Explicit process.platform win32 handling chooses Scripts/python.exe and
   `python`/`py`; Linux branch correctly uses .venv/bin/python3/python and
   python3/python. `split(/[\\/]/)` and chosen separator are cross-platform.
   No Pi code change required; configuration PYTHON is recommended.

4. artifacts/api-server/package.json:dev
   Conditional `process.platform === 'win32' ? 'pnpm.cmd' : 'pnpm'` is an
   intentional cross-platform branch. No change required.

5. machine-agent/scripts/build-agent.ps1, run-agent.ps1,
   package-windows.ps1
   PowerShell, target\ paths, jpackage MSI, WiX expectation, --win-console,
   --win-menu and --win-shortcut are Windows-only. Do not use/copy as launch
   mechanism on Pi. build-agent.sh is the Linux counterpart; no code change
   needed for building, but a Pi launcher/service is required.

6. machine-agent/src/main/java/.../ControllerSession.java:110, 673-688
   User-facing messages say "waiting for Windows", "COM port" and "Windows
   opened the COM handle". Function calls use requested port string and UGS
   JSerialComm rather than Windows APIs. Functional Linux operation should work
   with /dev/ttyUSB* or /dev/ttyACM*; wording needs a future code change.

7. Java tests only: DrawingAutomationTest, ControllerSessionInitializationTest,
   PortLeaseBookTest contain COM4/COM6/COM9 fixtures. They are test data, not
   production port defaults. Optional future test portability cleanup only.

8. local_desktop_app.py and start_local_project.bat contain hardcoded C:\ paths.
   No other production code contains Windows registry, Win32 API, Windows
   service API, native DLL loading, hardcoded browser path, cmd.exe, or .exe
   launch requirement. Existing .venv has Windows DLL/EXE artifacts and must
   not be copied.

9. machine-agent attached JARs are compiled artifacts of unknown OS/JDK
   provenance. They must not be assumed valid on ARM64; rebuild on Pi.

CNC / SERIAL / GRBL AUDIT
-------------------------
Files/classes:
- ControllerRegistry.java: creates head-1/head-2 sessions; lists devices via
  `ConnectionFactory.getDevices(ConnectionDriver.JSERIALCOMM)`; validates the
  requested path against enumerated devices and prevents one port being leased
  to both heads.
- ControllerSession.java: owns one UGS GrblController and port; connects via
  `openCommPort(ConnectionDriver.JSERIALCOMM, requestedPort, requestedBaudRate)`;
  initializes GRBL, receives status/pins/alarms, supports disconnect, reset,
  unlock, home, jog, work zero, raw command and streaming.
- SessionGrblController.java: preserves UGS command response ownership.
- GrblCommandBuilder.java: GRBL command construction.
- DrawingAutomation.java: explicit two-head automation with connection,
  homing/status/alarm safeguards and G-code stream control.
- PortLeaseBook.java: mutual exclusion by case-insensitive port name.
- MachineHttpServer.java: authenticated REST endpoints and SSE events.
- AgentConfig.java / Main.java: local-only listener at port 18888 by default.

Current port choice: UI/API sends a string selected from agent enumeration;
there is no hardcoded production COM number or baud rate. Profiles persist a
port and baud per head in the agent user's home directory. Tests use COM sample
strings only. API accepts profile baud rates 1200..2000000.

Linux expectation: UGS/JSerialComm enumeration should expose device paths such
as /dev/ttyUSB0 or /dev/ttyACM0; the source passes the selected string through
rather than enforcing COM syntax. On Pi, run the service account in `dialout`
(or the group owning the tty device), then log out/in or restart service. A
udev rule keyed to each adapter's serial number/vendor/product is strongly
recommended to create stable names (for example /dev/dmhc-head1 and head2),
because ttyUSB/ttyACM numbering can change after reconnect/reboot. Verify that
the adapter driver is in the kernel and that no ModemManager/serial console
holds the port. Do not run the production agent as root.

JSerialComm assessment: version 2.11.4 is explicitly pinned. Its upstream
documentation describes it as platform-independent, calls out Linux serial
permissions, and recognizes armv8_64 as a Linux architecture. It extracts a
native library; verify the JAR includes/loads the ARM64 native library under
the chosen ARM64 Java 17 runtime. If noexec prevents loading from temp, its
documented java.io.tmpdir or jSerialComm.library.path options may be relevant.

The Java source only uses portable java.nio filesystem APIs.

NODE / FRONTEND / API ANALYSIS
------------------------------
Node version: no package.json engines declaration. LOCAL_DEPLOYMENT_GUIDE says
Node 24; use a current Node 24 Linux ARM64 build and test it. pnpm version is
not pinned by packageManager/corepack metadata; use a currently compatible pnpm
version and retain frozen lockfile installs after initial validation.

Workspace packages: @workspace/api-server, @workspace/dmhc-ui,
@workspace/mockup-sandbox, @workspace/api-spec, @workspace/api-zod,
@workspace/api-client-react, @workspace/db, @workspace/scripts.
Root build: `pnpm run build`; root typecheck uses project references and then
artifact/scripts typechecks. API test: `tsx --test src/lib/*.test.ts`.

Runtime API: Express app has `cors()` with its unrestricted default behavior,
JSON/text 50 MB limits and routes under /api. It has no host binding argument,
so Node's default listener behavior must be considered when exposing it; retain
local-only/reverse-proxy design if LAN access is desired. UI Vite server/preview
binds 0.0.0.0 and allows all hosts. This is convenient on LAN but not a secure
public exposure configuration.

The frontend's relative /api calls work during Vite dev/preview because
vite.config.ts proxies /api to APPLICATION_API_TARGET (default 127.0.0.1:25309
outside Replit). For static production hosting, Vite proxy does not exist: a
reverse proxy or a combined same-origin server must route /api to Express.
The Machine Agent is deliberately separate and loopback-only; the browser UI
validates its URL as http + localhost/127.0.0.1/[::1], so a remote LAN browser
cannot control a Pi-hosted agent without a future deliberate architecture/UI
change. This is a security design, not a Pi bug.

PYTHON ANALYSIS
---------------
Expected version is not declared. Code uses modern typing syntax (`list[str]`,
`dict | None` in launcher), so Python 3.10+ is required; Python 3.11 is a
practical Raspberry Pi target. dmhc_em/main.py is command-line only: no tkinter
or GUI dependency. There is no serial package, no Windows platform check, and
no subprocess use in the regular G-code pipeline. Paths are pathlib/portable.

dmhc_em/image_to_gcode.py is separately portable in source but invokes
Potrace/vpype via shutil.which/subprocess and uses cv2/NumPy. It writes staged
PBM/SVG/config/G-code next to requested output, with atomic replacement. It
will need Linux executables on PATH. The active Express image endpoint does NOT
call that Python file: it has its own TypeScript raster/vector implementation
and requires ImageMagick. Consequently install only what features you enable.

STARTUP / ORCHESTRATION
-----------------------
Current Windows one-click flow:
1. start_local_project.bat finds .venv\Scripts\python.exe (or C:\gp\.venv),
   sets PYTHONPATH/PATH and launches local_desktop_app.py.
2. Launcher skips pnpm install if root node_modules exists; otherwise runs
   pnpm install.
3. Launcher detects occupied 25308/25309/18888 then executes PowerShell to
   force-kill owner processes.
4. It builds API, launches Node dist/index.mjs with PORT=25309.
5. It launches Vite with PORT=25308, BASE_PATH=/, host 0.0.0.0. Vite's proxy
   default is 127.0.0.1:25309, matching this launcher.
6. It uses an existing machine-agent/target JAR or Maven-builds it, then starts
   Java JAR at 18888, captures and displays generated agent token.
7. It opens http://127.0.0.1:25308/ via webbrowser and terminates child
   processes on Ctrl+C.

Recommended Pi architecture (proposed, not implemented):
- A systemd service for Java Machine Agent, user `dmhc`, local bind only.
- A systemd service for Express API, user `dmhc`, explicit PYTHON pointing to
  /opt/dmhc/.venv/bin/python3 and writable system temporary directory.
- A frontend production build served by nginx/Caddy/lighttpd (or Vite only for
  development), with same-origin /api reverse proxy to Express.
- Machine Agent stays at loopback 127.0.0.1:18888. Use the local browser on the
  Pi for direct control; do not expose its token/API remotely by default.
- A proposed start_raspberry_pi.sh may be useful for development, but services
  are safer for an always-on CNC controller. Add only after validation.

FINAL ANSWERS
-------------
1. Can it realistically run on Raspberry Pi ARM64? Yes, with a fresh native
   dependency build/install and hardware validation. It is not certified by
   this repository for Pi today.
2. Works without source modification: Java agent source conceptually, normal
   Python G-code partitioner, React/Express source, pnpm workspace, and Bash
   agent builder are Linux-capable. They still need Pi-specific installation.
3. Likely needs modifications: Windows one-click launcher; Windows MSI
   packaging; ControllerSession Windows-only diagnostic wording. Production
   deployment also needs added service/reverse-proxy/udev configuration.
4. Blockers: no fundamental source-level ARM blocker found. Operational
   blockers are unvalidated serial stack, absence of Pi startup setup, and
   missing ImageMagick when image endpoint is used.
5. JSerialComm/CNC viability: likely viable. JSerialComm 2.11.4 documents
   Linux ARMv8_64 support and Linux permissions. Treat actual UGS+USB adapter
   testing as mandatory before connecting motors or running production G-code.
6. Change before moving: do not change blindly. First plan a Linux launcher or
   systemd units, deployment ownership, dialout/udev rules, same-origin proxy,
   explicit PYTHON, and optional feature package policy. Remove Windows-only
   launch assumptions in a future reviewed change.
7. Test after moving: Node/pnpm install and UI/API build; agent Maven/UGS build;
   JSerialComm enumeration; both device paths/permissions/reconnects; one
   controller status read, then homing/jog/stream only with safety controls;
   UI proxy/API jobs; image conversion if enabled; shutdown/reboot persistence.
