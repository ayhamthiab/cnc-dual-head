FORENSIC DIAGNOSTIC: TWO-HEAD AUTOMATION INTERMITTENT HANG
============================================================

Scope
-----
This report analyzes the current repository only. No Java, TypeScript, or
configuration source code was modified for this diagnostic.

Executive conclusion
--------------------
The most likely cause is a worker thread stuck inside an unbounded UGS or
JSerialComm call, most likely while Head 1 is starting or issuing the Z jog.
DrawingAutomation then waits forever in CompletableFuture.allOf(...).join().
Because the worker is blocked rather than throwing, the workflow never reaches
the catch block and finishFailed() never runs. This exactly explains:

  Head 1 Z MOVE START
  Head 2 Z MOVE START
  Head 2 Z MOVE SUCCESS
  no Head 1 Z MOVE SUCCESS
  no [ERROR] block
  no completion message

The next most likely cause is the same unbounded UGS call occurring in a
status/refresh path, which can also make /health appear to hang. A JVM process
crash is possible in principle, but the source has no evidence that favors it
over the deterministic unbounded-wait path.

Ranked causes
-------------
1. HIGH: Unbounded UGS/JSerialComm call in Head 1's worker.
   ControllerSession.jog() is synchronized and calls
   GrblController.sendCommandImmediately(command), followed by
   restoreParserModalState() for legacy jogging and requestStatusReport().
   There is no Future timeout around those calls. The 120-second movement
   timeout starts only after session.jog(...) returns in ControllerRegistry.
   Therefore MOVE_TIMEOUT_MILLIS does not bound jog command submission.

   The same structural risk exists in ControllerSession.home(),
   setWorkZero(), startStream(), and other UGS calls made before their outer
   polling loops. In particular, setWorkZero() calls
   ControllerUtils.sendAndWaitForCompletion(active, command) without an
   explicit timeout argument. The pinned UGS helper's default overload is
   2000 ms in the local bytecode, but that is an implementation detail of the
   dependency, not a timeout contract owned by this application; command
   submission and other UGS calls remain unbounded.

2. HIGH: Unbounded two-head coordination.
   DrawingAutomation.runBoth() starts two tasks on a fixed two-thread
   headExecutor and then calls CompletableFuture.allOf(first, second).join().
   join() has no deadline. A completed Head 2 future cannot make runBoth()
   return while Head 1's future is still running.

3. MEDIUM: Health/status refresh blocked in UGS state access.
   MachineHttpServer uses a cached HTTP executor, so one stuck automation task
   does not inherently stop the HTTP listener. However, /health calls
   controllers.state(), which calls ControllerSession.snapshot() for both
   sessions. snapshot() synchronously refreshes UGS controller state and
   getters while holding each session's stateLock. If a UGS/JSerialComm getter
   is blocked, the health request itself remains pending. The frontend request
   has no AbortSignal or timeout, so its displayed state remains
   "Checking local agent..." until the browser/network request resolves.

4. MEDIUM: Lock interaction involving one ControllerSession.
   ControllerSession movement methods are synchronized. A worker blocked in
   jog(), home(), setWorkZero(), or another synchronized method holds that
   session monitor. Calls for the other head are isolated on a different
   ControllerSession, so the two sessions do not share that monitor. This is
   not a direct cross-head deadlock in the normal path, but it can block health,
   abort, disconnect, or manual calls that need the affected session or its
   stateLock.

5. LOW: Endpoint-level starvation.
   MachineHttpServer uses Executors.newCachedThreadPool(), not a single request
   thread. A blocked automation worker should not consume the HTTP executor.
   An endpoint can still become unresponsive when its synchronous controller
   snapshot or serial operation blocks, and repeated polling can accumulate
   pending request threads because the UI has no request timeout.

6. LOW: Java process crash or exit.
   Exceptions from head actions are wrapped in CompletionException and observed
   by allOf().join(), then passed to run()'s catch block. An ordinary worker
   exception should therefore produce finishFailed(), not terminate the JVM.
   The workflow, head, and serial-operation threads are daemon threads where
   explicitly configured; the HTTP server is still started by Main. A native
   serial-driver crash, JVM fatal error, OOM, external process termination, or
   batch-script shutdown would require runtime evidence not present in source.

7. LOW: Four-strike disconnect debounce.
   ensureCanContinue() only increments a per-head strike counter when a status
   snapshot says disconnected. It throws on strike four. It cannot block by
   itself. It can delay failure recognition by roughly four polling samples,
   and it can expose a stale/blocked status path, but it does not explain a
   worker that never returns from jog().

Exact execution path for the observed setup Z movement
-------------------------------------------------------
1. DrawingAutomation.run() reaches SETTING_WORK_ORIGIN and calls runBoth()
   for the two Z actions.

2. runBoth() submits Head 1 and Head 2 to headExecutor. The executor has two
   threads, so both normally begin concurrently.

3. Each action logs "Z MOVE START" and calls the registry's jogAndWait().

4. ControllerRegistry.jogAndWait() first calls session.snapshot(), then calls
   session.jog(...). The elapsed movement timer is initialized only after the
   session.jog() call returns.

5. ControllerSession.jog() is synchronized. It checks connection state,
   creates the command, installs a completion listener, calls
   active.sendCommandImmediately(command), possibly restores parser modal
   state, requests a status report, publishes an event, and returns a
   generation.

6. Only after that return does ControllerRegistry enter its while loop. The
   loop has a 120000 ms deadline, calls ensureCanContinue(), checks rejection,
   reads session.snapshot(), waits for accepted + idle + stable samples, and
   sleeps 50 ms between polls.

7. If Head 1 blocks in session.snapshot(), session.jog(), a UGS command call,
   requestStatusReport(), or a UGS getter used by refresh(), Head 1 never
   returns from its CompletableFuture.

8. Head 2 may finish normally and print "Z MOVE SUCCESS". Its future is then
   complete, but allOf(first, second).join() still waits for Head 1 forever.

9. Since no exception is thrown, run() does not enter either catch branch.
   finishFailed() is never called. Therefore no logFailure() call, no
   [Automation] [ERROR] block, no FAILED status, and no automation completion
   message are produced.

Are all movement/wait paths finite?
-----------------------------------
No.

Finite application-level waits:
  - Initial homing polling: caller supplies 180000 ms.
  - Setup jog polling: caller supplies 120000 ms.
  - Work-zero verification polling: caller supplies 10000 ms.
  - G-code stream polling: caller supplies 12 hours.
  - UGS initialization polling: 20000 ms.
  - Alarm-clear polling: 5000 ms.
  - Serial port open: Future.get(..., 10000 ms), with a stuck-driver flag.

Not fully bounded:
  - runBoth() uses allOf(...).join() with no timeout.
  - ControllerSession.jog() command submission and related UGS calls have no
    application-owned timeout.
  - ControllerSession.home() calls performHomingCycle() before the polling
    timeout starts.
  - ControllerSession.setWorkZero() performs command acknowledgement before
    the outer 10-second verification loop starts.
  - ControllerSession.startStream() calls queueStream()/beginStreaming() before
    the stream polling timeout starts.
  - ControllerSession.snapshot()/refresh() calls multiple UGS getters without
    a timeout. Every polling deadline is ineffective if one snapshot call
    blocks, because the loop cannot regain control to evaluate elapsed time.
  - HTTP fetches in the UI have no client-side timeout.

Exception propagation and cancellation
---------------------------------------
runUnchecked() converts an Exception into CompletionException. allOf().join()
would observe a completed exceptional future and run() would unwrap it and
call finishFailed(). That mechanism works for throw/fail cases.

It does not work for a hang. A hung task is neither complete nor exceptional,
so allOf() remains incomplete. The whenComplete() abort callbacks also do not
run for a still-running future. Even when one future fails, abortCompanionHead()
performs synchronous stop/reset calls and can itself wait on a session monitor
or serial operation; it is not a bounded cancellation mechanism.

shutdownNow() interrupts executor tasks, but it is only called by server stop
or shutdown. Interrupting a library call does not guarantee that UGS or native
serial code returns, and the code has no timed join/watchdog around the worker
future.

Would the process remain alive?
-------------------------------
Most likely yes. The workflow task and head executor threads are created as
daemon threads, but a stuck daemon worker does not crash the JVM. The HTTP
server remains started, and its cached request executor can create other
threads. A process exit would need separate evidence such as a JVM fatal log,
batch-script output, Windows Event Viewer evidence, or a missing process.

Should HTTP still respond?
--------------------------
Usually yes for endpoints that do not touch the affected UGS state. The HTTP
server has a cached thread pool, so the automation workflow does not occupy a
global request thread. However /health, /controllers, /status, and
/automation/status synchronously build snapshots. If UGS state access or the
DrawingAutomation synchronized snapshot is blocked, those requests can hang.
The UI's health fetch has no timeout, which makes a pending /health request
look exactly like a persistent "Checking local agent..." state. A separate
curl request to /health and a request to a trivial endpoint cannot be inferred
from the source alone; they are necessary runtime discrimination checks.

Why the debounce is not the primary cause
------------------------------------------
The debounce is evaluated only inside ensureCanContinue(), after
ControllerRegistry has regained control from session.snapshot(), session.jog(),
or another UGS call. Four disconnected samples can produce a normal exception
and then finishFailed(). It cannot fire while Head 1 is blocked in a library
call. At most, it delays a detected disconnect and may make a stale status look
temporarily connected/disconnected. The real failure remaining after debounce
strongly points to an unbounded call or coordination wait outside that logic.

Instrumentation to prove the diagnosis
---------------------------------------
Add temporary, timestamped entry/exit logs with runId, head id, thread name,
operation, generation, elapsed milliseconds, and outcome around:

  - runBoth() submit, each future completion, join start, join completion, and
    join timeout/cancellation.
  - Registry jogAndWait() before/after initial snapshot, before/after session.jog,
    first busy sample, accepted sample, every status sample duration, and loop
    deadline.
  - ControllerSession.jog() before/after sendCommandImmediately,
    restoreParserModalState, requestStatusReport, and the method return.
  - ControllerSession.snapshot()/refresh(), including each UGS getter duration.
  - abortCompanionHead(), stopStream(), and reset() entry/exit.
  - MachineHttpServer /health start/end and controllerState snapshot duration.

At the incident, capture:
  - jcmd <pid> Thread.print or jstack, twice about 5 seconds apart.
  - JVM stdout/stderr and the automation-run log.
  - HTTP timings for /health, /automation/status, /controllers, and a request
    that does not build controller state if available.
  - Process existence and exit code from the batch launcher.

The decisive stack evidence is Head 1's drawing-head thread. A stack in
sendCommandImmediately, requestStatusReport, a UGS communicator/native serial
call, or refresh getter proves the unbounded-call hypothesis. A stack parked in
CompletableFuture$ waiting code with both child futures inspected proves the
coordination wait. A stack in synchronized monitor acquisition identifies a
session-lock stall.

Minimal fix plan (not implemented)
----------------------------------
1. Give every UGS/serial operation an application-owned deadline, including
   command submission, homing initiation, work-zero acknowledgement, stream
   startup, status refresh, and cancellation. Run potentially blocking library
   calls through bounded helper futures and record timeout context.

2. Replace unbounded runBoth().join() with a bounded coordination policy. On
   timeout, cancel both futures, request bounded aborts, transition the run to
   FAILED with a timeout-specific error, and ensure the workflow can publish a
   terminal state even if a library worker remains stuck.

3. Make abort and cleanup best-effort and independently bounded; do not let
   cleanup block the only workflow thread that must publish failure.

4. Make health/status reporting use a nonblocking cached snapshot or bounded
   reads. Add a client-side fetch timeout so the UI changes from checking to an
   explicit offline/error state rather than remaining pending indefinitely.

5. Add regression tests with a fake head that blocks forever in jog initiation,
   snapshot, and command acknowledgement. Assert terminal FAILED status,
   diagnostic logging, companion abort attempt, and health-request behavior.

Final assessment
---------------
The strongest diagnosis is combination (1) + (3), with (4) as the concrete
mechanism: Head 1 can remain inside an unbounded ControllerSession/UGS call,
and runBoth() waits forever for it. The HTTP symptom is either a separate
blocked snapshot/health read or a UI request that remains pending; it does not
by itself prove that the Java process exited. The current source does not make
the stated guarantee that every movement/wait path has a finite end-to-end
timeout.
