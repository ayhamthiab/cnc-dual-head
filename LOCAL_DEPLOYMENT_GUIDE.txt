1. PROJECT OVERVIEW
===================

DMHC-EM currently consists of two different web/server paths and one local
hardware bridge:

1. The DMHC web frontend:
   - React 19 and TypeScript.
   - Built and served by Vite.
   - Source: artifacts/dmhc-ui/
   - Browser routes include the workspace, visualization, job history, and
     Machine Controller pages.

2. The Replit/API application server:
   - Express 5 and TypeScript.
   - Source: artifacts/api-server/
   - Mounted API prefix: /api
   - Runs the Python DMHC-EM compiler as a child process.
   - Stores job metadata in memory.
   - It is separate from the local Machine Agent.

3. The local Machine Agent:
   - Standalone Java 17 application.
   - Source: machine-agent/
   - Default URL: http://127.0.0.1:18888/api/v1
   - Runs on the computer physically connected to the Arduino/GRBL
     controllers.
   - Uses two isolated UGS Core GrblController sessions, one for Head 1 and
     one for Head 2.
   - It is intentionally loopback-only and does not expose serial ports to
     the internet.

4. UGS Core:
   - Only the ugs-core Maven module is used by the Machine Agent.
   - The UGS desktop GUI is not launched or required by the Agent.
   - Source pin:
     7c7d45b6b94a718589ce4b444865cd790c34882a
   - Source repository:
     https://github.com/winder/Universal-G-Code-Sender

5. Arduino/GRBL:
   - The Machine Agent discovers serial devices through UGS/JSerialComm.
   - The actual Arduino/GRBL controller is outside this repository and must be
     connected to the computer through USB/serial.
   - Real hardware, motors, limit switches, and homing behavior have not been
     validated by this repository.

6. Database:
   - lib/db/ is a PostgreSQL/Drizzle scaffold.
   - The schema currently contains no tables.
   - The API server currently uses an in-memory Map for jobs and does not use
     the database package.
   - A database is not required for the current CNC Machine Controller path.

7. External services:
   - Normal Machine Agent operation does not call a cloud service.
   - Building UGS Core may clone/fetch from GitHub and Maven may download
     dependencies.
   - The frontend references Google Fonts over HTTPS. Those font requests are
     external at runtime unless the fonts have already been cached or bundled
     locally.

Current data flows
------------------

Machine Controller path:

  Browser
      |
      | HTTP REST + Server-Sent Events
      v
  DMHC frontend
      |
      | direct fetch to http://127.0.0.1:18888/api/v1
      v
  Local Machine Agent
      |
      | UGS Core GrblController + JSerialComm
      v
  COM/USB serial device
      |
      v
  Arduino/GRBL controller

G-code processing path:

  Browser
      |
      | same-origin /api requests
      v
  DMHC frontend
      |
      v
  Express API server
      |
      | child process: python3 -m dmhc_em.main
      v
  Python DMHC-EM compiler
      |
      v
  head1.gcode / head2.gcode / gapfill.gcode / report.json

There is currently no API route that automatically sends a generated job to
the Machine Agent. The operator must download or otherwise obtain the
generated G-code and use the Machine Controller stream controls separately.
Gap Fill is not assigned to a physical controller by the Machine Agent.

4. FRONTEND STARTUP
====================

Install dependencies from the project root on Windows PowerShell:

  cd C:\path\to\project
  pnpm install

The root package is a pnpm workspace. Do not replace this with npm install or
yarn install.

Start the Vite development frontend from PowerShell:

  cd C:\path\to\project
  $env:PORT="25308"
  $env:BASE_PATH="/"
  pnpm --filter @workspace/dmhc-ui run dev

The frontend package script is:

  vite --config vite.config.ts --host 0.0.0.0

The configured artifact default is:

  Port: 25308
  URL:  http://localhost:25308/

The source Vite configuration requires both environment variables:

  PORT
  BASE_PATH

PORT is validated as a positive number and is used for both dev and preview
servers. BASE_PATH is used as Vite's base and by the Wouter router.

To use another local frontend port:

  $env:PORT="3000"
  $env:BASE_PATH="/"
  pnpm --filter @workspace/dmhc-ui run dev

The Machine Controller Agent URL is not a Vite environment variable. It is
defined in the browser UI and persisted in browser localStorage:

  Default: http://127.0.0.1:18888/api/v1
  URL key: dmhc.machine.agentUrl
  Token key: dmhc.machine.agentToken

There is no VITE_API_URL or frontend API URL environment variable in the
current source. The generated application API calls use relative /api paths.

The frontend also has these package scripts:

  pnpm --filter @workspace/dmhc-ui run typecheck
  pnpm --filter @workspace/dmhc-ui run build
  pnpm --filter @workspace/dmhc-ui run serve

Note for Windows:
  The API server's "dev" package script contains the POSIX shell expression
  "export NODE_ENV=development". That command is not a PowerShell command.
  The Windows procedure in this guide uses the API build and start commands
  separately instead.


5. PRODUCTION FRONTEND
=======================

Create the production frontend build:

  cd C:\path\to\project
  $env:PORT="25308"
  $env:BASE_PATH="/"
  pnpm --filter @workspace/dmhc-ui run build

Generated files are written to:

  artifacts/dmhc-ui/dist/public/

This output is a static frontend bundle. The DMHC web artifact configuration
serves that directory with a static service and rewrites unknown paths to
index.html:

  artifacts/dmhc-ui/.replit-artifact/artifact.toml

For a local Vite preview of the generated bundle:

  cd C:\path\to\project
  $env:PORT="25308"
  $env:BASE_PATH="/"
  pnpm --filter @workspace/dmhc-ui run serve

The package's serve script is:

  vite preview --config vite.config.ts --host 0.0.0.0

This serves the bundle at:

  http://localhost:25308/

There is no project-specific Windows static-server script other than Vite's
preview command. A generic static server can theoretically serve
artifacts/dmhc-ui/dist/public, but the exact command and SPA rewrite behavior
of that server are outside this repository and are therefore UNKNOWN here.

A separate web server is not needed for the static frontend itself. However,
the current frontend has no Vite proxy configuration and has no configurable
API base URL:

  - frontend origin: http://localhost:25308
  - API server origin: http://localhost:8080
  - frontend job requests: relative /api/...

Consequently, running these two processes on separate ports does not make the
job pages work automatically. The browser will request
http://localhost:25308/api/..., not http://localhost:8080/api/....

For the full web application, a same-origin reverse proxy or a combined web
server is required, or the frontend/API code must be changed to support a
separate API origin. No such local reverse-proxy configuration exists in the
current project. This is a current blocker for a one-command, fully local
deployment of all frontend pages.

The Machine Controller page is different: it explicitly calls the local
Agent URL and can work from the static frontend without the Express API
server, provided the browser can reach the Agent and CORS/token checks pass.

After JavaScript dependencies and any required assets are installed, the
frontend bundle itself does not need internet access to execute. Exact Inter
and Fira Code font downloads still depend on the Google Fonts references unless
the browser has cached them or the fonts are bundled separately.

7. API COMMUNICATION
====================

There are two separate APIs. They must not be confused.

7A. Express application API used by the G-code pages
----------------------------------------------------

Base prefix:

  /api

Current local server port from artifact configuration:

  http://localhost:8080

The frontend uses same-origin relative paths. The effective expected URL is
therefore normally http://<frontend-origin>/api/..., which is why a proxy or
same-origin server is needed when the API runs on port 8080 separately.

Endpoint: GET /api/healthz
  Purpose:
    Express API health check.
  Request body:
    None.
  Required headers:
    None.
  Response used:
    JSON {"status":"ok"}.
  Frontend use:
    Generated client exists, but no current UI call to this endpoint was found.

Endpoint: POST /api/process
  Purpose:
    Submit raw G-code to the Python DMHC-EM partitioning pipeline.
  Required headers:
    Content-Type: application/json.
  Request body:
    {
      "gcodeContent": "raw G-code text",
      "filename": "program.gcode",
      "numHeads": 2,
      "gapWidth": 10.0,
      "toolRadius": 0,
      "safetyMargin": 0,
      "head2ReferenceY": 1200.0,
      "penUpZ": 5.0,
      "penDownZ": -1.0,
      "gapStartY": null
    }
  Required field:
    gcodeContent.
  Defaults in the server:
    filename program.gcode
    numHeads 2
    gapWidth 10.0
    head2ReferenceY 1200.0
    penUpZ 5.0
    penDownZ -1.0
    gapStartY null
  Response used:
    JSON Job object. The Home page invalidates the job list and navigates to
    /viz/<job-id> after success.
  Important current behavior:
    The API accepts toolRadius and safetyMargin in the request schema, but
    jobs.ts stores toolRadius=0 and safetyMargin=0 and invokes the Python CLI
    with --radius 0 --margin 0. The submitted values are not currently used.

Endpoint: GET /api/jobs
  Purpose:
    List recent jobs.
  Request body:
    None.
  Required headers:
    None.
  Response used:
    JSON array of Job objects, used by the Job History page.
  Storage:
    In-memory Map; all records disappear when the API process restarts.

Endpoint: GET /api/jobs/:jobId
  Purpose:
    Get one job's status and metadata.
  Request body:
    None.
  Required headers:
    None.
  Response used:
    JSON Job object. The visualization page polls this endpoint every
    approximately two seconds until the job is terminal.

Endpoint: GET /api/jobs/:jobId/visualization
  Purpose:
    Return visualization data reconstructed from generated G-code and
    report.json.
  Request body:
    None.
  Required headers:
    None.
  Response used:
    JSON containing segments, densityMap, zones, and bounds.

Endpoint: GET /api/jobs/:jobId/download/head1
Endpoint: GET /api/jobs/:jobId/download/head2
Endpoint: GET /api/jobs/:jobId/download/gapfill
  Purpose:
    Download one generated G-code file.
  Request body:
    None.
  Required headers:
    None.
  Response:
    text/plain with Content-Disposition attachment.
  Frontend use:
    Download links appear on Jobs and Visualization pages.

Endpoint: POST /api/jobs/:jobId/invert
  Purpose:
    Return selected generated files with X and/or Y values inverted.
  Required headers:
    Content-Type: application/json.
  Request body:
    {
      "files": ["head1", "head2", "gapfill"],
      "invertX": true,
      "invertY": false
    }
  Validation:
    files must be a non-empty array containing only head1, head2, gapfill.
    At least one of invertX or invertY must be true.
  Response used:
    JSON object mapping each selected file key to inverted G-code text.

Express API implementation notes:
- artifacts/api-server/src/app.ts mounts the router at /api.
- cors() is called with its default permissive configuration.
- JSON and text bodies have a 50 MB limit.
- The server has no authentication middleware.
- jobs.ts creates temporary directories and invokes:

    python3 -m dmhc_em.main

- The API server passes PYTHONPATH=<workspace root> to that child process.
- The API has no route that connects processing jobs to the Machine Agent.

7B. Local Machine Agent API used by Machine Controller
-------------------------------------------------------

Base URL:

  http://127.0.0.1:18888/api/v1

The UI validates that the Agent URL:
- uses http, not https;
- has hostname 127.0.0.1, localhost, or ::1;
- ends exactly with /api/v1;
- has no query string or hash.

The UI's generic fetch wrapper appends the endpoint path to this base URL and
adds the following header when a token is present:

  Authorization: Bearer <agent-token>

POST requests created by the UI use:

  Content-Type: application/json

The following endpoints are called by artifacts/dmhc-ui/src/pages/machine.tsx.
The {id} value is Head 1 or Head 2.

GET /api/v1/health
  Purpose:

8. MACHINE AGENT INTEGRATION
============================

Agent executable:

  target/dmhc-machine-agent.jar

Default listener:

  http://127.0.0.1:18888/api/v1

The Agent binds only to 127.0.0.1 by default. AgentConfig rejects a public
host; this is intentional because the Agent controls physical serial devices.

Token behavior:
- DMHC_AGENT_TOKEN can provide a stable token.
- --token can provide a token for one invocation.
- If neither is provided, a random URL-safe token is created at startup.
- The token is printed by Main.java.
- The frontend stores the entered URL and token in that browser's localStorage.
- The frontend does not send the Agent token to the Express API server.

Authorization format:

  Authorization: Bearer <agent-token>

The Agent accepts that header for protected HTTP endpoints. For SSE, it also
accepts the token query parameter because standard browser EventSource does not
support custom request headers.

CORS implementation:
- MachineHttpServer.java checks the Origin host before adding CORS headers.
- Default allowed host suffixes are:
    .replit.dev
    .replit.app
    localhost
    127.0.0.1
- DMHC_ALLOWED_ORIGIN_SUFFIXES replaces the default set when non-empty.
- Allowed request headers:
    Authorization, Content-Type
- Allowed methods:
    GET, POST, OPTIONS
- Requests without an Origin are allowed for curl/local diagnostics.
- An invalid Origin receives HTTP 403.

For a local browser frontend served as http://localhost:25308, the default
Agent CORS allowlist includes localhost. The frontend can therefore call the
Agent directly if:
- the Agent is running;
- the URL is correct;
- the token is correct for protected endpoints;
- the browser is served over HTTP, not opened as a file;
- no local firewall or browser extension blocks loopback requests.

The current UI rejects remote Agent URLs, so the frontend cannot be configured
to use a remote Machine Agent without changing source code.

Offline changes required:
- No code change is required for the Machine Controller page to target the
  default local Agent URL.
- The Agent JAR and Java runtime must already be installed.
- The browser must be able to load the frontend from a local HTTP server.
- Google Fonts must be cached or replaced with local files if exact typography
  is required with no network.
- The full job-processing pages still need a local same-origin API arrangement;
  that proxy is not included.


9. CORS / LOCALHOST
===================

Frontend-to-Agent:

  http://localhost:<frontend-port>
      ->
  http://127.0.0.1:18888

This is cross-origin because the host and/or port differs. The Machine Agent
implements CORS itself. It answers OPTIONS requests and allows Authorization
and Content-Type headers for origins whose host matches its allowlist.

The current default allowlist covers:
- localhost
- 127.0.0.1
- Replit development domains
- Replit application domains

Therefore a frontend served at http://localhost:25308 can communicate with
the default Agent without an Agent code change, assuming the token and Agent
are correct.

Do not use a browser file URL such as file:///C:/.../index.html as the normal
deployment method. The current Agent's Origin handling does not explicitly
allow a file/null origin, and the frontend's relative /api job calls also
need an HTTP origin.

Frontend-to-Express API:

The Express server uses permissive cors(), but this does not solve the port
mapping problem. CORS can allow a cross-origin request, but the frontend still
does not know to send /api requests to port 8080. It sends them to its own
origin because the paths are relative.

Current result:
- Direct Machine Controller -> Agent: supported.
- Frontend job pages -> API on a separate port: not wired locally.
- A same-origin reverse proxy or application-server integration is required
  for the complete UI. No such configuration is present.


10. REPLIT DEPENDENCIES
=======================

The current project depends on Replit in these areas:

1. Artifact/workflow configuration:
   - .replit
   - artifacts/*/.replit-artifact/artifact.toml
   - Used to start services and provide preview/production routing in Replit.
   - Not needed by Java Agent runtime.
   - Can be bypassed locally by setting environment variables and running the
     package commands directly.

2. Vite development plugins:
   - @replit/vite-plugin-cartographer
   - @replit/vite-plugin-dev-banner
   - @replit/vite-plugin-runtime-error-modal
   - Cartographer and dev-banner are conditionally loaded only when
     NODE_ENV is not production and REPL_ID is defined.
   - The runtime-error-modal plugin is included by the Vite config.
   - These are not part of the Machine Agent hardware path.

3. Replit runtime modules:
   - .replit selects nodejs-24, python-base-3.13, java-graalvm22.3.
   - A clean Windows machine must install equivalent runtimes separately.

4. Replit preview routing:
   - The artifact router makes the web service available through Replit's
     preview path and routes the API artifact at /api.
   - This routing masks the fact that the UI uses relative /api URLs.
   - It is not reproduced by the current local commands.

5. Replit package configuration:
   - pnpm-workspace.yaml contains Replit package catalogs and platform
     overrides.
   - It explicitly removes several non-linux-x64 optional binaries, including
     Linux ARM/ARM64 variants for tools such as esbuild.
   - This is a Raspberry Pi compatibility risk.

6. Replit cloud/API server:
   - The Express server can run in Replit, but it is ordinary Node/Express
     code and can be run locally if Node, pnpm, and Python are installed.
   - It is not the hardware Agent and cannot access the local COM ports through
     the Agent architecture.

What breaks if Replit is unavailable:
- Replit preview routing and workflows are unavailable.
- Conditional development plugins are unavailable; normal Vite development
  remains possible if their packages are installed or production mode avoids
  them.
- The local Machine Agent itself does not need Replit.
- The browser Machine Controller can use a locally served frontend and the
  loopback Agent.
- The complete job UI needs a local solution for the relative /api paths.
- Google Fonts may not load unless cached or made local.

Intended offline machine-operation path:

      v
  Local Machine Agent :18888
      |
      v
  UGS Core
      |
      v
  COM/USB
      |
      v

No internet is required during normal Agent/controller operation after all
software, dependencies, drivers, and assets have been installed.

  cd C:\path\to\project\machine-agent

This step may require internet access for the UGS GitHub checkout and Maven

  target\dmhc-machine-agent.jar

Step 5 — Build the frontend
---------------------------

From a project-root PowerShell terminal:

  cd C:\path\to\project

---------------------------

For local development:

  cd C:\path\to\project
  $env:PORT="25308"

  cd C:\path\to\project

  pnpm --filter @workspace/dmhc-ui run serve

Open:

  http://localhost:25308/

Step 7 — Start the Express API server if processing/jobs are required
----------------------------------------------------------------------

In a second project-root PowerShell terminal:

  cd C:\path\to\project
  $env:PORT="8080"
  $env:NODE_ENV="production"
  pnpm --filter @workspace/api-server run build
  node artifacts/api-server/dist/index.mjs

This server is required for current Home, Jobs, and Visualization requests,

/api paths by itself. A local reverse proxy/same-origin configuration is still

Step 8 — Connect the Arduino/GRBL hardware
-------------------------------------------

Connect each controller and install its Windows serial driver. Confirm the
actual COM names in Windows Device Manager.

No connection or movement occurs just because the Agent starts.

Step 9 — Start the Machine Agent
--------------------------------

In a third PowerShell terminal:

  cd C:\path\to\project\machine-agent
  java -jar .\target\dmhc-machine-agent.jar

Expected base URL:

  http://127.0.0.1:18888/api/v1

Copy the token printed by the Agent. Do not paste it into a public document.

Step 10 — Configure Agent URL and token
---------------------------------------

In the browser:
1. Open Machine Controller.
2. Leave Agent API URL as:
     http://127.0.0.1:18888/api/v1
3. Enter the token printed by the Agent.
4. Click Save & check.
5. Confirm that the Agent status changes to online.

The URL and token are stored in this browser's localStorage. They are not sent
to the Express API server.

Step 11 — Verify communication
------------------------------

Agent health is token-free:

  curl.exe http://127.0.0.1:18888/api/v1/health

API health, if the Express server is running:

  curl.exe http://localhost:8080/api/healthz

Protected Agent diagnostics require the printed token:

  curl.exe -H "Authorization: Bearer <agent-token>" http://127.0.0.1:18888/api/v1/serial-ports

Step 12 — Verify Head 1
-----------------------

In Machine Controller:
1. Refresh Ports.
2. Select Head 1's actual COM port.
3. Select the actual baud rate.
4. Click Connect.
5. Confirm that Head 1 reports Connected and a firmware/status snapshot.
6. Verify MPos/WPos display only.
7. Read/refresh GRBL settings only after confirming the intended action.

Do not test physical motion until the work area is clear and the controller
hardware has been independently checked.

Step 13 — Verify Head 2
-----------------------

Repeat the same process for Head 2 using its own serial port and baud rate.
Head 1 and Head 2 are separate sessions. The Agent rejects a port that is
already owned by the other head.

Gap Fill has no assigned controller in the current implementation. Do not
send a generated Gap Fill program to a head by assumption.

- The actual JSerialComm native support for the selected Raspberry Pi OS and
  architecture must be verified.
- The UGS source commit must be built for the Pi's OS/architecture.
- USB serial device names and permissions must be verified on the Pi.

Frontend:
- A prebuilt static frontend can theoretically be served on a Pi without
  Node.js at runtime.
- Building the current Node workspace on ARM is not supported by an explicit
  compatibility guarantee.
- pnpm-workspace.yaml removes multiple ARM optional binaries, including
  esbuild Linux ARM/ARM64 variants and other platform packages.
- The current Vite/API build on ARM is therefore UNKNOWN and may fail.

Express API/Python:
- The API uses Node.js and invokes python3.
- Python code is generally portable in source form, but the API has no Pi
  configuration or service file.
- The API requires a Node runtime and Python installation if job processing is
  used.
- The current database is not required by the API routes in practice.

Windows-only parts:
- build-agent.ps1, run-agent.ps1, and package-windows.ps1 are Windows scripts.
- The MSI packaging path requires jpackage and WiX and is Windows-specific.
- COM naming in the documentation is Windows-oriented.
- The core Java source is not proven Windows-only, but Linux/Pi operation is
  not validated.

Likely rebuild requirements:
1. Install a Java 17 ARM-compatible JDK.
2. Build UGS Core and the Machine Agent natively for the Pi.
3. Verify JSerialComm native support on the exact Pi OS/architecture.
4. Add Linux serial permissions/udev configuration.
5. Replace the Windows-only MSI workflow with a Linux launch/service method.
6. Verify Node/pnpm/esbuild/Vite on ARM or copy a prebuilt frontend bundle.
7. Add a local same-origin frontend/API arrangement for job pages.
8. Test real Arduino/GRBL hardware and all safety paths on the Pi.

No Raspberry Pi deployment command is provided as an exact working command
because the repository does not provide or validate one.


16. PORTS
=========

COMPONENT                    DEFAULT PORT       PROTOCOL        PURPOSE
---------------------------  -----------------  --------------  ----------------
DMHC frontend dev/preview   25308              HTTP            Browser UI
Express API server          8080               HTTP            /api health/jobs
Machine Agent               18888              HTTP            /api/v1 local API
Machine Agent SSE            18888              HTTP/SSE        /api/v1/events
Mockup sandbox              8081               HTTP            Development only
Arduino/GRBL serial         No TCP port        USB/serial      Physical control

Port facts:
- 25308 is supplied by the dmhc-ui artifact configuration. Vite itself
  requires PORT and does not hardcode this value in source.
- 8080 is supplied by the api-server artifact configuration. Express itself
  requires PORT and does not hardcode this value in source.
- 18888 is the Machine Agent source default and the frontend default URL.
- 8081 is the mockup-sandbox artifact port and is not required for CNC use.
- SSE is not a separate server; it shares the Machine Agent HTTP port.

Changing ports:
- Frontend: set PORT and update the browser URL.
- Express API: set PORT and start the API with that value.
- Machine Agent: use --port or run-agent.ps1 -Port, then update the frontend
  Agent URL to the same port.
- A separate Express API port still needs a same-origin proxy or frontend/API
  integration because current frontend calls are relative /api paths.


17. EXACT STARTUP COMMANDS
==========================

QUICK START — WINDOWS
---------------------

These commands assume:
- pnpm dependencies are installed;
- the Machine Agent JAR has already been built;
- python3 is available if the API server is used.

TERMINAL 1 — FRONTEND

  cd C:\path\to\project
  $env:PORT="25308"
  $env:BASE_PATH="/"
  pnpm --filter @workspace/dmhc-ui run dev

Open:

  http://localhost:25308/

TERMINAL 2 — BACKEND (required for current job-processing features)

  cd C:\path\to\project
  $env:PORT="8080"
  $env:NODE_ENV="production"
  pnpm --filter @workspace/api-server run build
  node artifacts/api-server/dist/index.mjs

TERMINAL 3 — MACHINE AGENT

  cd C:\path\to\project\machine-agent
  java -jar .\target\dmhc-machine-agent.jar

Machine Agent URL:

  http://127.0.0.1:18888/api/v1

If the JAR does not exist yet, build it first:

  cd C:\path\to\project\machine-agent
  .\scripts\build-agent.ps1

The frontend and API processes can be built once and then started from their
generated outputs, but the exact full-application local proxy is not included.


18. TROUBLESHOOTING
===================

Frontend cannot reach Machine Agent
-----------------------------------
Actual causes to check:
- Agent JAR is not running.
- Agent is on a non-default port but the UI URL was not updated.
- UI URL does not end exactly in /api/v1.
- Browser token is empty or belongs to a previous Agent invocation.
- Browser Origin is not allowed by AgentConfig.
- A local firewall or browser policy blocks loopback HTTP.

Test the token-free health endpoint:

  curl.exe http://127.0.0.1:18888/api/v1/health

CORS error
----------
The Machine Agent owns its CORS rules. The Express API's cors() setting does
not affect the Agent.

For local UI use, serve the frontend at localhost and keep the Agent bound to
127.0.0.1. If using another hostname, set DMHC_ALLOWED_ORIGIN_SUFFIXES to the
needed host suffix and restart the Agent. The Agent never allows a public bind
host.

Agent token error / HTTP 401
----------------------------
Health is intentionally token-free, but serial, profiles, status, settings,
and control endpoints require:

  Authorization: Bearer <agent-token>

Copy the current token printed by the running Agent into Machine Controller
and click Save & check. Do not use a token from an earlier Agent process if the
token was generated automatically.

Connection refused on port 18888
--------------------------------
The Java Agent is not listening on that port, or another port was selected.
Check the Agent console and run:

  curl.exe http://127.0.0.1:18888/api/v1/health

Connection refused on port 8080
--------------------------------
The Express API is not running, PORT differs, or the build did not complete.
Run:

  curl.exe http://localhost:8080/api/healthz

Port already in use
-------------------
Vite uses strictPort and exits instead of silently selecting a different port.
Set another PORT before starting the frontend. Express also requires a free
PORT. The Agent accepts --port between 1024 and 65535.

Machine Agent running but frontend shows disconnected
-----------------------------------------------------
The UI checks the Agent health URL from the browser. Check:
- exact Agent URL;
- localhost/127.0.0.1 hostname;
- HTTP scheme;
- CORS Origin result;
- browser console;
- token for subsequent protected requests.

SSE connection failures
-----------------------
The UI uses:

  GET /api/v1/events?token=<agent-token>

EventSource cannot send the Authorization header. Verify the token query
parameter is accepted, the Agent CORS response allows the frontend origin, and
the Agent is still running. The UI logs "Live event stream disconnected;
reconnecting..." and the browser EventSource attempts reconnection.

API 404 errors
--------------
These are commonly caused by using the wrong server or path:
- Express health: /api/healthz
- Express jobs: /api/jobs...
- Agent health: /api/v1/health
- Agent controller API: /api/v1/heads/...

The Express root / may return 404 because no root route is defined.

If the frontend job pages request http://localhost:25308/api/... while the API
is listening at http://localhost:8080/api/..., this is the current missing
proxy/same-origin configuration, not an Agent failure.

Environment variable problems
-----------------------------
Vite fails at config evaluation if PORT or BASE_PATH is missing.
Express fails at startup if PORT is missing.
The Agent does not require an environment file; it reads optional Agent
variables and command-line arguments.
lib/db fails if imported without DATABASE_URL, but current API job routes do
not use it.

Missing npm packages
--------------------
Run from the project root:

  pnpm install

Do not use npm install or yarn install because the root preinstall guard
requires pnpm.

Wrong Node.js version
---------------------
The project configuration selects Node.js 24 but package.json does not declare
an engines constraint. Use Node.js 24 first. If another version is used,
verify pnpm install, Vite build, and API build independently.

Python compiler does not start
------------------------------
The API server invokes exactly:

  python3 -m dmhc_em.main

If Windows cannot resolve python3, the processing request fails even when
Node.js and the API server itself are running. The repository has no fallback
to python and no Windows Python launcher configuration.

UGS/Maven build fails
--------------------
The first Machine Agent build needs Java, Maven, Git, the pinned UGS source,
and Maven dependencies. The build scripts run git fetch and Maven installation.
If a compatible target/dmhc-machine-agent.jar already exists, runtime can use
that JAR without repeating the build, but its Java/OS compatibility must be
verified.

Head cannot connect
------------------
Check:
- the actual serial port is present in the Agent's /serial-ports response;
- no other program owns it;
- the selected baud rate is valid;
- the USB/serial driver is installed;
- the other head has not already claimed that port.

Do not infer that a connected serial port means motors, limit switches, or
homing are safe. The repository did not test those physical components.

Generated Gap Fill handling
---------------------------
The current Machine Agent has only Head 1 and Head 2 controller sessions.
Gap Fill is not assigned to a controller. Do not send Gap Fill automatically.


19. FINAL LOCAL ARCHITECTURE
============================

The currently supported direct local controller path is:

  Browser
      |
      | HTTP + SSE
      v
  Local DMHC Frontend
      |
      | REST:
      | http://127.0.0.1:18888/api/v1
      | SSE:
      | http://127.0.0.1:18888/api/v1/events?token=...
      v
  DMHC Local Machine Agent :18888
      |
      | UGS Core 2.0-SNAPSHOT
      | JSerialComm serial discovery
      v
  COM4 / COM5 / another detected serial device
      |
      | USB/serial
      v
  Arduino/GRBL Controller
      |
      v
  CNC Head 1 or CNC Head 2

The separate current G-code processing path is:

  Browser
      |
      | same-origin /api requests
      v
  Frontend
      |
      | requires local same-origin proxy for a separate port
      v
  Express API Server :8080
      |
      | python3 -m dmhc_em.main
      v
  Python DMHC-EM Compiler
      |
      v
  head1.gcode / head2.gcode / gapfill.gcode / report.json

The complete intended offline arrangement therefore needs both branches, plus
a local same-origin routing solution for the Express API:

  Browser
      |
      v
  Local frontend HTTP server
      |\
      | \
      |  \-- /api (same-origin proxy) --> Express API :8080
      |                                      |
      |                                      `--> Python DMHC-EM
      |
      `---- direct localhost REST/SSE ----> Machine Agent :18888
                                               |
                                               `--> UGS Core
                                                     |
                                                     `--> USB/serial
                                                           |
                                                           `--> Arduino/GRBL

No component in the current source automatically connects the generated
processing output to a selected physical head. The operator must select and
control the intended Head explicitly.
